# Work Memory / Work Trace
## 基本設計書

**文書ステータス：Draft 0.1**  
**目的：就労能力可視化基盤のシステム基本設計**

---

## 1. システム目的

Work Memory / Work Traceは、実際の仕事で発生する作業履歴をWork Traceとして記録し、Work Item単位に整理・分析することで、個人の就労能力、適性、作業上の摩擦、必要支援、能力を発揮しやすい条件を可視化する基盤である。

本システムは単純な勤怠・工数管理や従業員監視を目的としない。

---

## 2. 基本アーキテクチャ

```text
実際の仕事
   ↓
Work Trace Capture
   ↓
Work Item Association
   ↓
Security / AI Processing Gateway
   ↓
FACT
   ↓
ANALYSIS
   ↓
Human Validation
   ↓
KNOWLEDGE
   ↓
Personal Work Capability Profile
```

処理は完全な直列処理ではなく、イベント収集・紐付け・分析を重複して進められるスパイラル型とする。

---

## 3. 主要コンポーネント

### 3.1 Work Trace Capture

仕事中に発生するイベントを記録する。

対象例：
- 作業開始・終了
- 文書閲覧
- Web調査
- メール
- 電話
- 他者への質問・相談
- 他者からの依頼
- 割り込み
- 再作業・手戻り
- 完了フォロー

人間による入力を最小化し、自動取得可能な情報は自動取得する。

### 3.2 Work Item Association

各Work Traceを、対応するWork Itemへ紐付ける。

ここが本システム最大の技術的ゲートである。

自動判定だけで完結させず、
- 暫定紐付け
- ワンタップ訂正
- 未分類トレイ
- 後からの一括割当
を提供する。

### 3.3 Security / AI Processing Gateway

データ分類に応じてAI処理経路を制御する。

原則：
- 外部AIはデフォルト禁止
- 機密データは内部AIまたは処理禁止
- 許可されたデータのみ外部AIへ送信可能
- 匿名化・最小化を可能にする
- 全AI処理を監査可能にする

### 3.4 Fact Store

観測・申告された事実を保存する。

FACTは、
- observed：システム等から観測
- reported：本人等による申告
を区別する。

矛盾が発生した場合、片方を消去せず「要確認」として両方を保持する。

### 3.5 Analysis Engine

FACTを材料としてAIが分析・仮説生成を行う。

ANALYSISはFACTへ自動昇格させない。

### 3.6 Knowledge Store

繰り返し確認された有用な知見を再利用可能なKnowledgeとして保存する。

AIは昇格候補を提示するが、最終的な昇格は人間が承認する。

---

## 4. Work Item

Work Itemは仕事のまとまりを表す基本単位である。

例：
- 案件
- タスク
- 依頼
- 問い合わせ対応
- 電話対応
- 文書作成
- 調査
- 複数日にまたがる仕事

Work Traceは原則としてWork Itemに関連付ける。

ただし関連付けが確定できない場合は、未分類状態を許容する。

---

## 5. 自動紐付け方針

優先順位：

1. メール件名・スレッド
2. チャットスレッド
3. 開いている文書・ファイル
4. 最近アクティブだったWork Item
5. 時刻・参加者・キーワード等の補助情報
6. AIによる意味的推定

電話や突発的割り込みなど、意味的手掛かりが少ないイベントは誤紐付けより未分類を優先する。

---

## 6. 人間による訂正

自動紐付け結果は必ず訂正可能とする。

訂正操作は原則1～2操作以内で完了できるUIを目標とする。

訂正時間そのものを測定し、システム導入による記録負担を評価する。

---

## 7. データ処理モデル

### FACT

「何が起きたか」を表す事実データ。

### ANALYSIS

FACTからAI等が導出した仮説・分析。

### KNOWLEDGE

検証済みで再利用可能になった知識。

この3層を混在させない。

---

## 8. セキュリティ設計

最低限、以下を実装対象とする。

- データ分類
- アクセス制御
- AI処理可否判定
- 外部AI送信制御
- 監査ログ
- 保持期間管理
- Knowledgeへの機密区分継承
- AIバックエンド交換可能設計

Knowledgeは元となったFACT/派生データの機密区分を継承する。

---

## 9. 記録負担対策

システムが「仕事を記録するための仕事」にならないことを重要な非機能要件とする。

方針：
- 自動取得を優先
- 一行メモ・音声入力を許容
- AIによる後整理
- 些細な操作を全て記録しない
- 実際の入力時間を機械的に計測

---

## 10. 非機能要件

### 操作性

日常業務を妨げないこと。

### 可監査性

FACTの出所、AI分析、Knowledge昇格を追跡可能にする。

### 可訂正性

誤ったWork Item紐付けを容易に訂正できること。

### 可拡張性

AIバックエンド、入力ソース、分析モデルを交換可能にする。

### プライバシー

従業員監視・ランキング用途への無制限な転用を防止する。

---

## 11. 最小実証実験

初期実験は10 Work Itemsとする。

対象パターン：

1. 電話
2. メール
3. 文書閲覧
4. Web調査
5. 他者依頼
6. 割り込み
7. 並行案件
8. 完了フォロー
9. 複数日

10件ではスクリーニング実験として扱い、統計的な最終結論とはしない。

---

## 12. GO / STOP基準

| 指標 | GO | STOP |
|---|---:|---:|
| 自動紐付け成功 | 7/10以上 | 5/10以下 |
| 誤紐付け | 1件以下 | 3件以上 |
| 平均訂正時間 | 10秒以下 | 20秒以上 |
| 未分類率 | 30%以下 | 50%以上 |

中間値はグレーゾーンとし、20件まで実験を拡張する。

基準は実験結果を見てから変更しない。

また、総合値がGOでも特定パターンで重大な失敗が発生した場合は、そのパターンを個別にSTOP判定できる。

---

## 13. スコープ外

初期段階では以下を実装しない。

- 全社規模の従業員監視
- 従業員ランキング
- 生産性ランキング
- 人事評価の完全自動化
- 全PC操作の完全監視
- 無制限の外部AI利用
- Brain Twinとの全面統合
- 高度なダッシュボード
- Knowledgeの完全自動昇格
- 全活動の完全自動意味理解

## 14. 将来アーキテクチャ

```text
Work Trace
    ↓
FACT Repository
    ↓
Analysis Engine
    ↓
Knowledge Repository
    ↓
Personal Work Capability Profile
    ↓
本人 / 支援者 / 職場 / 人事
```

将来的には、本人の認識、支援者の観察、職場評価、実作業データを統合し、就労支援・業務設計・合理的配慮・職業適性の判断材料として利用する。

ただし、人間を単一スコアで評価する設計にはしない。

---

## 15. 設計上の最重要原則

> **「人の能力を点数化する」のではなく、「人・仕事・環境・支援の適合関係をデータから発見する」。**

この原則を、本システムの全設計・実装・評価に適用する。
